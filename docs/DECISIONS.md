# Decisions

Why Clara 1.0 is built the way it is. The plan ([clara-rebuild-plan.md](../clara-rebuild-plan.md)) set the direction;
the questions below were answered by the owner before the rewrite (October 2026); the last section lists the choices
made while building, to be confirmed or changed.

## Answered by the owner

| Question | Decision |
| --- | --- |
| Scope of the rewrite | All six phases of the plan |
| How releases are made | GitHub Releases built by CI (`release.yml`); the repository is public; CI pushes the sandbox image to ghcr.io and each release pins it by digest |
| Containers for scripts | Rootless Podman only; no Docker fallback (rootful Docker is refused) |
| Service layout | A system unit and a dedicated `clara` user |
| Python tooling | uv with a committed `uv.lock` |
| Web site | Svelte 5 with TypeScript, built in a pinned Node image (no Node on the machine) |
| Web site design | The first site's design (Cyanotype: Prussian-blue rail in both themes, Hanken Grotesk and Epilogue, Clara's portrait as the mark, the favicon and beside answers, line icons), on the 1.0 layout, with the conversation list moved into the rail |
| Web site navigation | The pages you work in stay in the rail, the list of conversations under them on every page (the logo and New chat stay put, the rest of the rail scrolls as one); Memory, Connections, Rules & approvals, Models, Usage and Admin sit under one **Settings** entry with a tab bar; waiting approvals show as a button at the foot of the rail, alerts as a count on Settings |
| Web site readability | Two steps under the first site's sizes (body 13 px, answers and what you write 14 px, small text 11.5 px; titles 16 px), muted text darker (lighter in dark theme): about 6:1 against the page instead of 5:1 |
| Checkboxes | Drawn, not the browser's: a 16 px box with a 2 px border that fills violet with a white tick, the same in both themes |
| Theme | Auto / Light / Dark switch in the rail, remembered in the browser; each colour is written once as `light-dark()` (browsers from 2024), so the two themes cannot drift apart |
| Special tools | Tool **packs**, available in chats and in schedules. In a chat they sit behind a **"+" menu** that replaced the attach button (files are one entry of it, with web search, the second brain and the project); a switch is saved with the conversation, so it follows it to every client; Discord and the terminal get `/tools` |
| Special tools: what a pack is | A name for a group of tools that exist only where it is on; it never grants permissions (the rule gate still decides). Reading a day back (conversations, activity, files) is a pack of its own, off by default |
| Special tools: privacy | An incognito conversation is never read back. A local-only conversation is read only from a local-only conversation. What a conversation nobody may read made (a task, a note, a file) stays out too |
| Files of a day | A short catalogue (reference, what happened, who, lines changed, a few words) and a tool that reads one file on demand, whole or as the day's diff: the content is paid for only when Clara asks. Sources: the workspace, the vault, the Drive files she created, the files you sent |
| Schedules: runs | A schedule can have a conversation per run, a model, and packs; a run can ask you one question and **wait** (`waiting`), your answer arriving in the run's conversation; the next run can close the old one from what it has |
| Schedules: missed and overlapping runs | Two choices per schedule: for runs missed while the server was off, skip / run the latest / run them all; for a run that comes due before the last is over, skip / close the old and start the new / queue the new one |
| The daily note | A schedule made once at start (enabled, every day at 23:59, French prompt you can edit), replacing the built-in recap. Clara reads the day with the packs' tools, asks one question on the web site and Discord (a thread in `#general`), waits, writes one block « Récap (Clara) » of the daily note, marks only the tasks you confirm, and the thread is deleted at the end |
| Web site tokens | One scale each for type (9 steps, in rem), space (a 2px grid), shape, motion and stacking; no literal colour, size or space outside the token block ([WEB-DESIGN.md](WEB-DESIGN.md)) |
| Web site questions | A dialog (a native `<dialog>`: inert page, Tab trapped, Escape cancels), never the browser's `confirm()` or `prompt()`: they ignore the theme, cannot mask a secret, and a browser may switch them off |
| Web site accessibility | Every control named, state carried by ARIA attributes, text 4.5:1 and marks 3:1 in both themes, targets of 24 px at least (36 px on touch), a skip link, focus kept in drawers and dialogs |
| Chat transcript | The first site's: tool calls folded into one line per run, line icons instead of emoji, the context ring |
| Discord bot token | The bot's own systemd credential, never in Clara's database |
| Licence | None: all rights reserved |
| "Remember nothing" | Incognito conversations: no facts read or written, deleted 24 hours after their last message (`CLARA_INCOGNITO_HOURS`) |
| Versions of answers (edit, ask again) | Kept |
| Markdown files Clara writes | Merged into the workspace, folder `notes/` (git history, undo) |
| The vault | Seven tools behind `open_second_brain`, opened per conversation |
| Google Drive | `drive.file` scope and the Google Picker |
| Mail (this lifts the non-goal « email connectors ») | Gmail and Outlook through their own APIs with OAuth, never a password: Gmail with `gmail.readonly` and `gmail.compose` (later `gmail.modify` too, see « Mail: labels and the Trash »; a token of its own, not Drive's), Outlook with Graph `Mail.ReadWrite` and `Mail.Send` for personal and work accounts. One mailbox of each |
| Mail: what Clara may do | Search and read; read an attachment's text, keep it in the workspace, send workspace files as attachments; save drafts; send. No label, archive, delete or settings |
| Mail: the three classes | `mail_read` and `mail_draft` are allowed everywhere; `mail_send` asks in a chat, is refused unattended, is at the `destructive` level (the Discord token cannot approve it), and is raised to ask after untrusted content whatever the rules |
| Mail: reading allowed everywhere | The owner chose « allow everywhere » over « ask when unattended »: a schedule may read the inbox without a prompt. A rule can ask or refuse (`mail_read`, target `mail:outlook`); reads taint the turn either way |
| Mail: what is sent | Only to the addresses in the call, shown whole in the approval request (the text up to 6,000 characters, so nothing hides past the part you read). The target of a send is each recipient (`mail:to:<address>`), so « allow always » can never open sending in general |
| Mail: labels and the Trash (this reverses « No label, archive, delete or settings » for those two) | Clara may list the person's labels, make one, add or remove them on a message, and move a message to the Trash. Not archive, filters or settings, and never a permanent delete: the scopes gain `gmail.modify` (it cannot delete for good), and no code calls `messages.delete`. A label is named from the person's own labels only, so a system label (INBOX, UNREAD) cannot be touched: that is what keeps « label » from meaning « archive ». Every Gmail connection made before this asks once more | `connectors/gmail.py` (`SCOPES`), `connectors/mail_tools.py` (`_label_ids`) |
| Mail is a pack, off by default | The mail tools are one pack, « Mail », that the « + » menu switches on for a conversation, like the web. Off, the tools are not offered at all: a chat that does not need mail does not carry them, and Clara says in the prompt that the pack is off. A hook gets the pack from the tools its allow-list names; a schedule that called a mail tool before keeps it (migration 0016, from the audit log) | `packs/registry.py`, `triggers/setup.py`, migration 0016 |
| Mail: a trash asks, and « Approve all next » covers it after mail was read | The owner chose this over the rule that a tainted turn raises outside-world writes: a sort of many mails must not ask for each one. A trash is `destructive`, so the Discord token cannot approve it; it is `ask` in a chat and held unattended. The cost is named: a message that steers Clara can ask for trashes, and a grant that is pressed covers the next ones of the same tool (up to its limits). A trashed mail stays in the Trash, which is why it is the one outside write a grant covers | `GRANTABLE` in `gate/grants.py`, `mail_trash` in `gate/actions.py` (not in `RAISED_WHEN_TAINTED`) |
| Mail: a label is allowed in a chat, held unattended | A label is reversible, and the Mail pack is the switch that brings it. Unattended, labels and trashes wait for the person | `mail_label` in `gate/actions.py` |
| Mail: the read mark, and deleting a label (this lifts « mark read » from the non-goals) | Clara may take the unread mark off a message, allowed in a chat and held unattended like a label. It removes UNREAD and nothing else, so it cannot archive. She may also delete one of the person's labels: it asks every time at the `destructive` level, is raised after untrusted content, is held unattended, and « Approve all next » does not cover it, because a deleted label cannot be taken back. A label delete is `labels.delete` (which `gmail.modify` covers), never `messages.delete`: the messages stay, without the label | `mail_mark` and `mail_label_delete` in `gate/actions.py`, `connectors/gmail.py` (`delete_label`) |
| Hooks (event-driven runs) | When a mail arrives, Clara can run: a *trigger* you write (a filter on the mail, a prompt, the tools allowed). First version: the core, the mail source, the API, the console and a **Hooks view on the Automation page**. GitHub pull requests and pushes came next (see the rows below). See « Time » in FEATURES.md |
| One Automation page, not a page per kind | The rail's « Schedules » page became **Automation**, with a switch between its views (Schedules, Hooks) at first: what Clara does by herself is one place however she is set off, and the next kind of trigger is one more choice, not one more link in a rail that already has five. « One list, one form » replaced the switch. The old address `#/schedules` is redirected, since the page is the same one | `pages/Automation.svelte`, `MOVED` in `lib/state.svelte.ts` |
| Automation forms in steps | The schedule and hook forms are told in steps (**Trigger, Action, Tools, Runs, Review**; a hook that only notifies has no Tools step) instead of one long form with a « More options » fold. Going back is free, going on is not: **Next** (and Enter, and a later step in the bar) keeps you on a step that has a name, a prompt, a time or a number missing or invalid, says what, and puts the focus on the field; the last step reads everything back in words; a short choice (repeat, what a hook does, the trigger, what to do with a missed or overlapping run) is a set of radios that shows every answer and what it means, not a dropdown. The entry was one **New schedule** / **New hook** button per view; it is now one **New automation** button (« One list, one form ») | `components/Wizard.svelte`, `components/Choice.svelte` |
| One list, one form | Schedules and hooks share one list on the Automation page, one **New automation** button and one form. Its first step is the trigger (at a time, or one of the events); the steps after it show only what fits that choice: a time has no conditions and no notify-only action, and a GitHub repository is picked from the ones added on Connections, not typed. The server keeps its two resources (`/v1/schedules`, `/v1/triggers`), so the form sends each to its own: the page changes, the API, the runs and the events do not | `pages/Automation.svelte` |
| One Library page for the workspace and the vault | Both are « the files Clara keeps »: a git folder she writes in and an Obsidian vault she reads, and each had a link of its own in the rail. They are two views of one page, **Library**, with the workspace's Files, History and Script runs kept as small tabs under its view. The old addresses `#/workspace` and `#/vault` are redirected (to `#/library`, and `#/library?view=vault`) | `pages/Library.svelte`, `MOVED` in `lib/state.svelte.ts` |
| An answer goes on when the web page is closed | The web asks for `keep_running`: the server drives the turn in a task of its own and the stream only follows it; leaving the page or the conversation does not stop it, **Stop** is an explicit `DELETE /v1/conversations/{id}/run`, and coming back follows the same run from its first event (`GET …/run`, an in-memory log of the running turn, token runs joined). Opt-in and web only: for the terminal and the Discord bot a closed stream is still a stopped answer (Ctrl-C and a restarted bot must stop it), and that is what `FEATURES.md` documents for the API. A kept answer waits for approvals as before (`CLARA_APPROVAL_WAIT`) rather than ending in two pieces; the cost is a turn nobody watches for up to that long | `agent/runs.py`, `tests/test_runs.py` |
| The tool-round limit says so | An answer that used its `CLARA_MAX_TOOL_ROUNDS` ended on whatever the model wrote without tools, often « one last check… ». The last round now follows a `warning` and a note to the model (not stored) to say what it found and what is missing | `ROUNDS_USED` in `agent/turn.py` |
| Discord: a thread is made whole | A turn that starts in a conversation with no thread used to make the thread from that one question (the live path knew nothing else), so a conversation switched into the history later reached Discord at its latest question, its earlier turns coming after the answer when the sync caught up. The live `start` event now carries the stored turns (`earlier`, only while there is no thread) and the bot starts the thread with the first question, writes the earlier turns in order, then posts the new question. A conversation that is idle when its project is switched on is still not sent until it next changes: only a new turn makes the thread (switching on does not make a thread for every old conversation at once) | `Watch.see`, `Mirror.thread_for` in `clara_discord/mirror.py`, `tests/test_discord_mirror.py` |
| Discord: an automation run's first message shows its origin | The first message of a run is the automation's instructions and the data it works on (a mail, a pull request), several Discord messages, when the owner wrote the instructions and needs first to see what started the run. The thread now starts with where the run came from: the events' own titles, one line each, five at most and then « +N more » (a hook), and the name with the moment it was due (a schedule, which has no outside origin; its documents are not named). Visual only, for the kinds `schedule` and `hook`: the model is given the whole message and the question is stored whole, so the quarantined reader's rule holds (a mail's subject is displayed, and never reaches the conversation through this path). The text is built from the events and the schedule when the run starts and **stored with the question** (`messages.shown`, migration 0028), not read back from the message or from the `events` table: a schedule that keeps one conversation puts several trigger messages in one thread, and old events are pruned. A message made before has none and is written as it was, so no thread already on Discord is rewritten. The web site keeps the whole message until the owner says otherwise | `triggers/message.py::shown_of`, `timekeeping/schedules.py::shown_of`, `mirror/service.py`, `tests/test_mirror.py`, `tests/test_triggers.py`, `tests/test_schedule_runs.py` |
| Web search: Brave first, SearXNG after | A research session of ~100 searches in two hours got Clara's address refused by every engine SearXNG scrapes (Brave and Google CSE: 429, DuckDuckGo: captcha, then timeouts), and « No result. » hid why, so the model kept retrying. The Brave Search API (a key, an official quota) comes first when a key is set; SearXNG stays as the fallback and the only search without a key; a service that cannot answer is told with its reason, and « nothing matches » is only ever a service that answered. The owner chose the fallback over a hard failure, and one place for the key: the Admin page's Secrets tab. A Connections card that checked the key with a test search before keeping it was built and dropped, as a second place for a secret the Secrets tab already holds; so nothing checks the key when it is saved, and a key Brave refuses shows as the `brave` alert while the search falls back. Other providers are kept for later, behind the same chain | `connectors/web.py`, `tests/test_connectors.py`, migration 0014 (`connections.kind` may be `brave`: applied, now unused, kept because a database at version 14 would be refused without it) |
| Secrets: grouped, each linked to its provider | The Admin page's Secrets tab was one flat table of names. It is a panel per service (model providers, web search, GitHub, Google, vault and backups), and each secret links to the page of its provider where the value is made, so setting one up is a click, not a search. The links live in the server (`SECRET_SOURCES`, with a test that every known secret has one), never in the client and never from a request or a model: a link on a page that asks for credentials must be one the code names. They open in a new tab with `noopener noreferrer`, so the provider is not told the address of your Clara. The refresh tokens link to Connections instead and cannot be set by hand (the server already refused it; the page offered the button for one of the two). Only addresses confirmed in each provider's own documentation are used: Mistral and Brave link to their consoles, whose key pages the documentation does not give | `secrets/store.py`, `pages/Admin.svelte`, `tests/test_foundations.py` |
| Hooks: a stop | Mail that arrived while Clara was off is handled by the trigger's `catch_up`, **`all` by default**, at the pace of `max_per_hour`; `latest`, `digest` and `skip` are per-trigger choices |
| Hooks: sending | A hook run may send only if you add an explicit rule; there is no per-trigger override. (A run is tainted from its first word, so the rule does not make a send silent: it still asks, whatever the rule says) |
| Hooks: conversations | One conversation per run, grouped **under the hook** in the web history like a schedule's (a `hook` group; listed only when the hook's `in_history` is on). A hook no longer makes a project of its own; it may name one for context files, as a schedule may. It first did make one, and the "folder" was then a project: files nobody put there, a second place to switch the history on, and a Projects page full of « Hook: … ». Migration 0010 deletes those projects when they hold nothing else; deleting a hook leaves its conversations as ordinary ones, because the link is its runs |
| Hooks: tools | With none listed, a run gets the event kind's read tools and `notify` only (mail: search, read, read attachment). Anything more is listed on the trigger |
| Hooks: a run the stop cut | Not run again if it had begun (Clara cannot know what it did); the trigger's `rerun_interrupted` opts in. One that had done nothing starts again |
| Hooks on GitHub: polled, not called | A pull request or a push is found by a poll of the repositories you added (`CLARA_GITHUB_POLL_SECONDS`), only for the kinds a hook waits for. GitHub cannot reach a machine that is on the tailnet only, and a webhook route would be a fourth path open without a token (`OPEN_PATHS`); the cost is a delay of a poll, which the owner accepted | `connectors/github_watch.py`, `NON-GOALS.md` |
| Hooks on GitHub: nothing is `self_caused`; every change asks | The token is the owner's, so Clara's commits and the owner's look the same: marking the token's account as « Clara » would hide the owner's own pushes and pull requests from every hook, the main use of one. The owner chose to let a hook see everything and to control a loop by consent instead: a hook's run is tainted from its first word, so each GitHub change (`github_write`, `github_branch`, `github_pr`, `github_issue`; commit, delete, branch, comment, merge, close) asks, whatever the rules say, and a loop turns only as fast as the owner approves, at most `max_per_hour`. The one way round is `tainted_rule` off together with a rule that allows `github_*` to unattended runs | `tests/test_github_hooks.py::test_a_hook_run_cannot_change_github_without_asking_even_when_a_rule_allows_it` |
| Hooks on GitHub: a first look starts from when the repository began to be waited for | The poll is only every `CLARA_GITHUB_POLL_SECONDS`, so a baseline taken at the poll lost what happened between adding the repository (or making the hook) and the poll: a pull request merged a minute after the owner added the repository was never seen. A pull request's times are GitHub's, so the first look starts there, never further back than `STALE_AFTER` (a server that was off replays nothing) and ten seconds earlier for the rounding and clock skew. A push cannot: the heads before the look are unknown | `GitHubWatch._began`, `tests/test_github_hooks.py::test_what_happens_between_adding_the_repository_and_the_first_look_is_not_lost` |
| Hooks on GitHub: a push is dated from the last look | GitHub's branch list gives the head of each branch, not when it was pushed; a commit's own date can be years old (a rebase, a cherry-pick). The last successful look is the honest bound, and it makes a push found after an outage a backlog for `catch_up`, as a mail found late is | `GitHubWatch._push` |
| Hooks on GitHub: the `diff` action of `github_read` | A hook that reviews a pull request needs its changes; the file reader cannot show them (a fork's branch is not in the repository). A pull request's files or a commit's, cut per file and in all, are one more read, not a new tool | `GitHub.diff` |
| Mail: new-mail notifications | Opt-in (`mail_notify`), a poll every `CLARA_MAIL_POLL_SECONDS`, sender and subject only, to every client; on its own loop, which the watchdog does not count |
| Facts from tainted turns | Kept, shown to the model tagged `[unconfirmed]` until you confirm |
| Tainted-turn rule | On by default |
| Discord and approvals | Discord may answer approvals except destructive ones |
| Client-side tools protocol | Kept in the API (`clara-chat --local-tools` uses it) |
| Reminder wording | Written by the model at fire time, the stored text as the fallback |
| Remote backups | restic |
| Conversations across clients | One shared list |
| Local-only flag | Per conversation |
| Discord bot features | Approval buttons, the event relay, files and pictures, slash commands |
| Conversations on Discord: a forum per project, automation and place, a thread per conversation | Discord allows 500 channels per server and 50 categories, and a chat makes a conversation every day; a thread is not counted as a channel, and a forum's posts are the natural shape of a list of conversations. A project, schedule or hook is one category with one forum; the loose conversations are the main forum; the incognito ones have their own. Local-only conversations are never on Discord: the local-only promise holds | `clara_discord/mirror.py`, `mirror/service.py` |
| Discord mirror: the server says what should be there, the bot makes it and reports the ids | The bot is a client like any other, with its own token: it cannot read the database. The server keeps the ids Discord gave, and works out each change from what it holds; the bot only does what it is told and reports back. Only what changed since the last revision is sent (`mirror_rev`, one clock for every change) | `mirror/clock.py`, `api/discord.py` |
| A deleted thread or forum on Discord asks you on the web site before anything is deleted here | Deleting on Discord is a click the bot's token can make; deleting a conversation or a project is not something a token may do alone. The request is destructive, so only the web site and the terminals answer it. The model is never offered `discord_forget` | `tools/discord_tools.py`, `gate/approvals.py` (`ask_outside`) |
| The answer is written in Discord as it is written here, and the stored answer then replaces it | A live feed (not stored: a bot that misses it still gets the stored answer at its next sync) carries the turn's text and tool calls; the bot edits one message until the end, then the digest of the stored text decides what is left to write | `mirror/live.py`, `mirror/service.py` (`Watch`) |
| Discord's archive and an archived conversation: read, never written | An archive in Clara is kept whole and takes no message; Discord's own archive after a week follows it, and a message posted there reopens a conversation archived by Discord, not one archived by you | `api/chat.py` (409), `clara_discord/bot.py` (`reopen`) |
| Discord layout | A private server with you and the bot only; four text channels found by id: `#general` (chat), `#approval`, `#notification`, `#alerts`; no direct messages; plain messages in `#general` (the privileged Message Content intent); reminders, tasks, schedules, hook results and update news go to `#notification` by default; which channel carries each of twelve categories is yours to choose on the Admin page (Discord tab), except approvals (`#approval`) and the questions of scheduled runs (`#general`) |

| `ask_questions` blocks the turn; a QCM does not | Claude Code's way for the questions Clara needs answered to go on (a preference, a missing detail): the turn pauses, the questions replace the box you write in, and your answers are the result of the call, so she continues in the same answer. | A QCM is answered one question at a time, in the side panel, and each answer is corrected at once | As in NotebookLM: a question alone, lettered options, a hint, the explanation after you answer, a score at the end with Retry. | The side panel lists the workspace files Clara wrote in the conversation, found from the git history | Every workspace commit already carries the conversation's id, so nothing new is stored and the cards survive a reload; the logs of scripts (`runs/`, written by the host) are left out, and a file that no longer exists is not offered. A card is a name, a folder, a time and a download, never the content; the Library stays the place for the whole workspace |
| The side panel also lists the vault notes Clara created or edited, and a card opens its file in the Library | The owner wanted the notes Clara adds to the second brain beside the files, and a click to lead to the Library instead of downloading. The vault's commits did not carry the conversation, so each commit Clara makes in a conversation now ends with `Conversation: <id>` as the workspace's do (a line in the vault's own git history, and on its remote, chosen over a table in Clara's database so that git stays the one truth); notes written before it are not listed. The list is read from git: a note she created and then changed is still "created", a moved one is at its new path, a deleted one is gone, hidden folders and templates are left out. A file or a note is a link (`#/library?path=…`, `#/library?view=vault&note=…`) so it opens in a new tab too; a file keeps a Download button, a note has none (the vault has no raw download) |
| The side panel is closed until something arrives, and remembers what you did | It opens by itself on the first card unless you closed it, and on a QCM when Clara makes one (that is what asks something of you); your choice is kept in the browser. On a phone it is a drawer over the page, like the navigation rail. The chat keeps a small chip where a QCM was made, which opens it in the panel |
| A project is made in steps, with a card for each choice | The owner asked for the automation form's design: the same stepped `Wizard` (Basics, Content, Tools, Review) and `Choice` cards, a card for each way to start (upload files, a folder, a GitHub repository, empty) and for each special tool. Nothing is stored until the last step is confirmed; the files are sent after the project exists, and if that fails the project is kept and says so (they can be added from its page) |
| A project says which special tools its new conversations start with | The owner wanted, say, Mail in every conversation of a project without switching it on each time. The project stores `packs` and `Conversations.create` copies them into a conversation made in it, whichever client makes it, unless the request names its own. It is a starting point, not a rule: the "+" menu still changes a conversation, a conversation already begun keeps its tools, and changing the project's list changes only the next ones. A tool the server cannot give yet can be ticked (it stays hidden from Clara until it can be used) |
| The QCM is a pack, off by default, and no conversation is migrated | `qcm` is a special tool like Mail or web search (`qcm` pack, chats only; the web chat still the only client that shows one).
