# Decisions

Why Clara 1.0 is built the way it is. The plan ([clara-rebuild-plan.md](../clara-rebuild-plan.md)) set the direction;
the questions below were answered by the owner before the rewrite (October 2026); the last section lists the choices
made while building, to be confirmed or changed.

## Answered by the owner

| Question | Decision |
| --- | --- |
| Scope of the rewrite | All six phases of the plan |
| How releases are made | GitHub Releases built by CI (`release.yml`); the repository is public; CI pushes the sandbox image to ghcr.io and each release pins it by digest |
| Containers for scripts | Rootless Podman only; no Docker fallback (rootful Docker is refused) |
| Service layout | A system unit and a dedicated `clara` user |
| Python tooling | uv with a committed `uv.lock` |
| Web site | Svelte 5 with TypeScript, built in a pinned Node image (no Node on the machine) |
| Web site design | The first site's design (Cyanotype: Prussian-blue rail in both themes, Hanken Grotesk and Epilogue, Clara's portrait as the mark, the favicon and beside answers, line icons), on the 1.0 layout, with the conversation list moved into the rail |
| Web site navigation | The pages you work in stay in the rail, the list of conversations under them on every page (the logo and New chat stay put, the rest of the rail scrolls as one); Memory, Connections, Rules & approvals, Models, Usage and Admin sit under one **Settings** entry with a tab bar; waiting approvals show as a button at the foot of the rail, alerts as a count on Settings |
| Web site readability | Two steps under the first site's sizes (body 13 px, answers and what you write 14 px, small text 11.5 px; titles 16 px), muted text darker (lighter in dark theme): about 6:1 against the page instead of 5:1 |
| Checkboxes | Drawn, not the browser's: a 16 px box with a 2 px border that fills violet with a white tick, the same in both themes |
| Theme | Auto / Light / Dark switch in the rail, remembered in the browser; each colour is written once as `light-dark()` (browsers from 2024), so the two themes cannot drift apart |
| Special tools | Tool **packs**, available in chats and in schedules. In a chat they sit behind a **"+" menu** that replaced the attach button (files are one entry of it, with web search, the second brain and the project); a switch is saved with the conversation, so it follows it to every client; Discord and the terminal get `/tools` |
| Special tools: what a pack is | A name for a group of tools that exist only where it is on; it never grants permissions (the rule gate still decides). Reading a day back (conversations, activity, files) is a pack of its own, off by default |
| Special tools: privacy | An incognito conversation is never read back. A local-only conversation is read only from a local-only conversation. What a conversation nobody may read made (a task, a note, a file) stays out too |
| Files of a day | A short catalogue (reference, what happened, who, lines changed, a few words) and a tool that reads one file on demand, whole or as the day's diff: the content is paid for only when Clara asks. Sources: the workspace, the vault, the Drive files she created, the files you sent |
| Schedules: runs | A schedule can have a conversation per run, a model, and packs; a run can ask you one question and **wait** (`waiting`), your answer arriving in the run's conversation; the next run can close the old one from what it has |
| Schedules: missed and overlapping runs | Two choices per schedule: for runs missed while the server was off, skip / run the latest / run them all; for a run that comes due before the last is over, skip / close the old and start the new / queue the new one |
| The daily note | A schedule made once at start (enabled, every day at 23:59, French prompt you can edit), replacing the built-in recap. Clara reads the day with the packs' tools, asks one question on the web site and Discord (a thread in `#general`), waits, writes one block « Récap (Clara) » of the daily note, marks only the tasks you confirm, and the thread is deleted at the end |
| Web site tokens | One scale each for type (9 steps, in rem), space (a 2px grid), shape, motion and stacking; no literal colour, size or space outside the token block ([WEB-DESIGN.md](WEB-DESIGN.md)) |
| Web site questions | A dialog (a native `<dialog>`: inert page, Tab trapped, Escape cancels), never the browser's `confirm()` or `prompt()`: they ignore the theme, cannot mask a secret, and a browser may switch them off |
| Web site accessibility | Every control named, state carried by ARIA attributes, text 4.5:1 and marks 3:1 in both themes, targets of 24 px at least (36 px on touch), a skip link, focus kept in drawers and dialogs |
| Chat transcript | The first site's: tool calls folded into one line per run, line icons instead of emoji, the context ring |
| Discord bot token | The bot's own systemd credential, never in Clara's database |
| Licence | None: all rights reserved |
| "Remember nothing" | Incognito conversations: no facts read or written, deleted 24 hours after their last message (`CLARA_INCOGNITO_HOURS`) |
| Versions of answers (edit, ask again) | Kept |
| Markdown files Clara writes | Merged into the workspace, folder `notes/` (git history, undo) |
| The vault | Seven tools behind `open_second_brain`, opened per conversation |
| Google Drive | `drive.file` scope and the Google Picker |
| Mail (this lifts the non-goal « email connectors ») | Gmail and Outlook through their own APIs with OAuth, never a password: Gmail with `gmail.readonly` and `gmail.compose` (a token of its own, not Drive's), Outlook with Graph `Mail.ReadWrite` and `Mail.Send` for personal and work accounts. One mailbox of each |
| Mail: what Clara may do | Search and read; read an attachment's text, keep it in the workspace, send workspace files as attachments; save drafts; send. No label, archive, delete or settings |
| Mail: the three classes | `mail_read` and `mail_draft` are allowed everywhere; `mail_send` asks in a chat, is refused unattended, is at the `destructive` level (the Discord token cannot approve it), and is raised to ask after untrusted content whatever the rules |
| Mail: reading allowed everywhere | The owner chose « allow everywhere » over « ask when unattended »: a schedule may read the inbox without a prompt. A rule can ask or refuse (`mail_read`, target `mail:outlook`); reads taint the turn either way |
| Mail: what is sent | Only to the addresses in the call, shown whole in the approval request (the text up to 6,000 characters, so nothing hides past the part you read). The target of a send is each recipient (`mail:to:<address>`), so « allow always » can never open sending in general |
| Hooks (event-driven runs) | When a mail arrives, Clara can run: a *trigger* you write (a filter on the mail, a prompt, the tools allowed). First version: the core, the mail source, the API, the console and a **Hooks view on the Automation page**. GitHub pull requests and pushes came next (see the rows below). See « Time » in FEATURES.md |
| One Automation page, not a page per kind | The rail's « Schedules » page became **Automation**, with a switch between its views (Schedules, Hooks) at first: what Clara does by herself is one place however she is set off, and the next kind of trigger is one more choice, not one more link in a rail that already has five. « One list, one form » replaced the switch. The old address `#/schedules` is redirected, since the page is the same one | `pages/Automation.svelte`, `MOVED` in `lib/state.svelte.ts` |
| Automation forms in steps | The schedule and hook forms are told in steps (**Trigger, Action, Tools, Runs, Review**; a hook that only notifies has no Tools step) instead of one long form with a « More options » fold. Going back is free, going on is not: **Next** (and Enter, and a later step in the bar) keeps you on a step that has a name, a prompt, a time or a number missing or invalid, says what, and puts the focus on the field; the last step reads everything back in words; a short choice (repeat, what a hook does, the trigger, what to do with a missed or overlapping run) is a set of radios that shows every answer and what it means, not a dropdown. The entry was one **New schedule** / **New hook** button per view; it is now one **New automation** button (« One list, one form ») | `components/Wizard.svelte`, `components/Choice.svelte` |
| One list, one form | Schedules and hooks share one list on the Automation page, one **New automation** button and one form. Its first step is the trigger (at a time, or one of the events); the steps after it show only what fits that choice: a time has no conditions and no notify-only action, and a GitHub repository is picked from the ones added on Connections, not typed. The server keeps its two resources (`/v1/schedules`, `/v1/triggers`), so the form sends each to its own: the page changes, the API, the runs and the events do not | `pages/Automation.svelte` |
| One Library page for the workspace and the vault | Both are « the files Clara keeps »: a git folder she writes in and an Obsidian vault she reads, and each had a link of its own in the rail. They are two views of one page, **Library**, with the workspace's Files, History and Script runs kept as small tabs under its view. The old addresses `#/workspace` and `#/vault` are redirected (to `#/library`, and `#/library?view=vault`) | `pages/Library.svelte`, `MOVED` in `lib/state.svelte.ts` |
| Hooks: a stop | Mail that arrived while Clara was off is handled by the trigger's `catch_up`, **`all` by default**, at the pace of `max_per_hour`; `latest`, `digest` and `skip` are per-trigger choices |
| Hooks: sending | A hook run may send only if you add an explicit rule; there is no per-trigger override. (A run is tainted from its first word, so the rule does not make a send silent: it still asks, whatever the rule says) |
| Hooks: conversations | One conversation per run, grouped **under the hook** in the web history like a schedule's (a `hook` group; listed only when the hook's `in_history` is on). A hook no longer makes a project of its own; it may name one for context files, as a schedule may. It first did make one, and the "folder" was then a project: files nobody put there, a second place to switch the history on, and a Projects page full of « Hook: … ». Migration 0010 deletes those projects when they hold nothing else; deleting a hook leaves its conversations as ordinary ones, because the link is its runs |
| Hooks: tools | With none listed, a run gets the event kind's read tools and `notify` only (mail: search, read, read attachment). Anything more is listed on the trigger |
| Hooks: a run the stop cut | Not run again if it had begun (Clara cannot know what it did); the trigger's `rerun_interrupted` opts in. One that had done nothing starts again |
| Hooks on GitHub: polled, not called | A pull request or a push is found by a poll of the repositories you added (`CLARA_GITHUB_POLL_SECONDS`), only for the kinds a hook waits for. GitHub cannot reach a machine that is on the tailnet only, and a webhook route would be a fourth path open without a token (`OPEN_PATHS`); the cost is a delay of a poll, which the owner accepted | `connectors/github_watch.py`, `NON-GOALS.md` |
| Hooks on GitHub: nothing is `self_caused`; every change asks | The token is the owner's, so Clara's commits and the owner's look the same: marking the token's account as « Clara » would hide the owner's own pushes and pull requests from every hook, the main use of one. The owner chose to let a hook see everything and to control a loop by consent instead: a hook's run is tainted from its first word, so each GitHub change (`github_write`, `github_branch`, `github_pr`, `github_issue`; commit, delete, branch, comment, merge, close) asks, whatever the rules say, and a loop turns only as fast as the owner approves, at most `max_per_hour`. The one way round is `tainted_rule` off together with a rule that allows `github_*` to unattended runs | `tests/test_github_hooks.py::test_a_hook_run_cannot_change_github_without_asking_even_when_a_rule_allows_it` |
| Hooks on GitHub: a first look starts from when the repository began to be waited for | The poll is only every `CLARA_GITHUB_POLL_SECONDS`, so a baseline taken at the poll lost what happened between adding the repository (or making the hook) and the poll: a pull request merged a minute after the owner added the repository was never seen. A pull request's times are GitHub's, so the first look starts there, never further back than `STALE_AFTER` (a server that was off replays nothing) and ten seconds earlier for the rounding and clock skew. A push cannot: the heads before the look are unknown | `GitHubWatch._began`, `tests/test_github_hooks.py::test_what_happens_between_adding_the_repository_and_the_first_look_is_not_lost` |
| Hooks on GitHub: a push is dated from the last look | GitHub's branch list gives the head of each branch, not when it was pushed; a commit's own date can be years old (a rebase, a cherry-pick). The last successful look is the honest bound, and it makes a push found after an outage a backlog for `catch_up`, as a mail found late is | `GitHubWatch._push` |
| Hooks on GitHub: the `diff` action of `github_read` | A hook that reviews a pull request needs its changes; the file reader cannot show them (a fork's branch is not in the repository). A pull request's files or a commit's, cut per file and in all, are one more read, not a new tool | `GitHub.diff` |
| Mail: new-mail notifications | Opt-in (`mail_notify`), a poll every `CLARA_MAIL_POLL_SECONDS`, sender and subject only, to every client; on its own loop, which the watchdog does not count |
| Facts from tainted turns | Kept, shown to the model tagged `[unconfirmed]` until you confirm |
| Tainted-turn rule | On by default |
| Discord and approvals | Discord may answer approvals except destructive ones |
| Client-side tools protocol | Kept in the API (`clara-chat --local-tools` uses it) |
| Reminder wording | Written by the model at fire time, the stored text as the fallback |
| Remote backups | restic |
| Conversations across clients | One shared list |
| Local-only flag | Per conversation |
| Discord bot features | Approval buttons, the event relay, files and pictures, slash commands |
| Discord layout | A private server with you and the bot only; four text channels found by id: `#general` (chat), `#approval`, `#notification`, `#alerts`; no direct messages; plain messages in `#general` (the privileged Message Content intent); reminders, tasks, schedules, hook results and update news go to `#notification` by default; which channel carries each of twelve categories is yours to choose on the Admin page (Discord tab), except approvals (`#approval`) and the questions of scheduled runs (`#general`) |
| Discord bot start | The server starts it as a child process when `CLARA_DISCORD_AUTOSTART=true` (the bot keeps its own process and token); `clara-discord.service` remains the other way, never both |

## Confirmed from the plan

- One token per client (terminal, web, console, Discord bot, each script), not one shared token.
- Scripts have no network unless a run asks for it and you approve.
- Python 3.12 is the baseline (CI also runs 3.13).
- A new repository, versioned 1.0; nothing is migrated from the old server, which stays readable for a few weeks.

## Made while building (to confirm)

| Choice | Why | To change |
| --- | --- | --- |
| A run that waits is a normal chat conversation (kind `chat`), linked to its run in `schedule_runs` | It shows in the list on every client and can be answered anywhere; a new conversation kind would mean rebuilding the `conversations` table (its `CHECK`) | — |
| The daily-note schedule is made once, marked in the `settings` table | You can edit, pause or delete it, and it is not made again | Delete the `daily_note_schedule` setting row to have it made again |
| A tool with no date means the day of the scheduled run it is in (the local date of its due time) | A run due at 23:59 and started after a stop still means the day that ended | The `date` argument |
| A waiting run is reminded once, at `CLARA_WAITING_REMIND_AT`, after three hours at least | One nudge, not a stream | The setting |
| `ask_person` reaches Discord only if the conversation is not local-only | Discord is outside the machine | — |
| A streamed chat waits 10 minutes (`CLARA_APPROVAL_WAIT`) for an approval, then goes on without the action; the request stays valid 24 h, and a later answer runs it and starts a short follow-up turn | You often answer within a minute; a turn should not hang for a day | The setting |
| `POST /v1/chat` (not streamed) never waits: the request is pushed to your clients | A script calling the API cannot answer an approval itself | — |
| A chat request not answered in 60 s is pushed to your other clients too | You may have walked away from the screen | — |
| Tokens look like `clara_<id>_<secret>` | The id finds the row without a scan; the prefix lets secret scanners (Clara's own, GitHub's) recognise a leaked token | — |
| Approval scopes per token: `all` (web, terminal, console), `safe` (Discord: not destructive), `none` (scripts) | The plan's Discord risk, and scripts must never approve their own requests | `/tokens approvals` |
| Secret-looking content leaving the machine raises to `ask`; secrets are never stored as facts | The review's item 10 | — |
| Forgotten facts leave a tombstone (their folded text) | Otherwise the model saves the same fact again at once | — |
| `search_history` searches earlier conversations (FTS5) | The review's item 28 | — |
| The answer budget counts model time only, not time waiting for you or for tools | Waiting for an approval should not eat the budget | `CLARA_ANSWER_BUDGET` |
| A model silent past the first-token timeout hands over to the next fallback; a spent budget does not | A stalled provider is the commonest outage; nothing was said, so nothing repeats | — |
| Updates go through `clara-launcher`: the server exits 75 for an update, 76 for a restart; the launcher switches the `current` link and rolls back | The new code is checked before the old one stops, and something outside the server can undo a failed start | — |
| Rule specificity: fields set, then literal characters in the target, then in the tool, then strictness | Predictable and explainable in the test box | — |
| Local-only conversations also hide the web, GitHub, Drive and mail tools, and the gate refuses anything leaving the machine (vault changes too when the vault pushes) | "Local only" must hold for tool calls, not only for the model | — |
| A message carries 4 files and 34 MB in all | Base64-encoded, that fits the 48 MB request limit (the review's item 51) | — |
| The tool count, routes, settings and alerts in FEATURES.md are checked by a test | The review's item 50 | — |
| Release signing is optional but, once `CLARA_RELEASE_PUBKEY` is set, required | A public repository; a GitHub account takeover should not be enough to ship code to the machine | `scripts/release_signing.py new` |
| GitHub Actions are pinned by major version, updated by Dependabot pull requests | Commit-SHA pinning is stronger; it can be switched to when the workflows settle | `.github/` |
| Gmail has its own token and shares Drive's redirect address | A Drive token must not gain mail powers, and Drive's `drive.file` token must not be attachable as a mailbox (a sign-in is bound to the connection it was started for); using Google's existing redirect means one address less to register | `connectors/gmail.py`, `api/connections.py` |
| Microsoft `Mail.ReadWrite` for drafts | Graph has no draft-only permission. The alternative (`Mail.Read` and `Mail.Send` only) leaves Outlook without drafts | The registration's permissions, and `outlook.py` |
| Sending is `destructive` | An email cannot be taken back, and it keeps a Discord account takeover from sending mail: the Discord token (scope `safe`) cannot approve it. The price: approvals of emails are answered on the web site or the console, or on Discord after `/tokens approvals <the bot's token> all` | `gate/actions.py`, the token's scope |
| A draft is allowed, and not raised after untrusted content | It stays in your mailbox until you send it yourself, and the request to send is what is guarded | `mail_draft` in `gate/actions.py` |
| No « send this draft » tool, and no recipient chosen by Clara | A draft can be edited after it was shown, so an approval of it would not describe what is sent; a send names its addresses and carries its whole text, which is what the request shows | — |
| The text of an email to send is 6,000 characters at most | The request shows all of it (8,000 characters for this class, 500 for the others); a longer text would hide a tail you never read | `MAX_BODY` in `connectors/mail.py` |
| 5 emails per answer | A loop of sends is stopped long before the approvals pile up | `SENDS_PER_TURN` in `connectors/mail_tools.py` |
| A new-mail notification carries the sender and the subject | The text then passes through Discord's servers when Discord is a listener; the body never does. What Clara writes *about* a mail is another matter: an automation set to deliver to Discord (`deliver`), or `discord_say`, sends it, and the owner chose that | `connectors/mail_watch.py`, `events/delivery.py` |
| The mail tools are hidden in a local-only conversation | Like Drive's and GitHub's: a search or a read is a call to the provider, and « local only » means nothing leaves. A local model on a normal conversation reads mail without sending it to a hosted model | `OUTSIDE_TOOL_PREFIXES` |
| Gmail attachments to send: 7 MB in all; Outlook: 2.2 MB each, 10 MB in all | Gmail carries the message in one JSON request; Graph takes an attachment in one request of 3 MB. Bigger files need upload sessions | `connectors/gmail.py`, `outlook.py` |
| A hook's run is tainted from its first word, with an allow-list of tools, and so is every later turn in its conversation | An event is untrusted content with no person watching: the tainted-turn rule must hold before the model has read anything, and a follow-up after an approval must not have more tools than the run | `ChatRequest.tainted`, `only_tools`, `Agent.restrictions` |
| A hook's events carry a preview, not the mail | The run reads the body with `mail_read` if it needs it; less of a stranger's text in the prompt, and in the database | `mail_event` in `connectors/mail_watch.py` |
| No regular expression in a filter | The subject is written by a stranger and the pattern by you: a pattern that backtracks without end would stop the server. Equal, contains, starts with, ends with and does-not-contain cover mail | `triggers/matching.py` |
| A backlog is what is found more than 15 minutes after it happened | Mail is polled every two minutes, so a few minutes' lateness is normal; more means the server was off or the provider was out | `STALE_AFTER` in `triggers/service.py` |
| The mail poll forgets its place when nobody listens | Otherwise a hook made today would replay the mail of the days since the last listener; the same flaw made turning notifications on announce a week of mail | `MailWatch.poll` |
| Mail from Clara's own account is left out unless the trigger says `include_self` | A hook that answers mail must not answer its own answer. (Not for GitHub: see above) | `self_caused` |
| 20 runs an hour, 500 waiting, 2 hooks at once | A thousand-mail outage costs a thousand model calls only as fast as you allowed; the model has its own slots too | `triggers/service.py` |
| Hooks are not a tool of the model | Like rules: a message must not be able to create a persistent hook | `api/triggers.py`, `/triggers` |
| A run says how it ended with a `schedule` event | Discord already routes it to `#notification`; no new event kind to teach every client. What tells it from a scheduled task's summary is its `source` (`triggers`) and its `status`, which is what lets you send hook failures to `#alerts` | `Triggers._tell`, `events/routing.py` |
| Each automation says where its result goes: `deliver` = `notice`, `web`, `discord` or `both`; the default is `notice`, what automations always did | A mail summary you can answer from your phone is a conversation, not a ping. Making that the default would have turned every existing schedule's short line in `#notification` into a long message that takes over your Discord chat. A failed run always tells the `notice` way: a failure is not a conversation | `events/delivery.py`, migration 0012 |
| A message to answer is an `ask` event of stage `said`, and its conversation becomes the bot's current one; no new event kind, no thread | The owner chose a plain message in `#general` that becomes the current chat over a thread per result. The bot already did this for a question with no thread; the web never gets it (targets: `discord`). The price: it replaces the conversation you were in on Discord until `/new` or the next such message. A conversation that has a thread gets it in the thread, and the current chat is left alone | `clara_discord/bot.py` (`deliver_ask`) |
| The whole answer of a run goes to Discord, up to 6,000 characters (an `ask` event); other events keep 2,000 | A hook's notification keeps the first paragraph (700 characters) because it is a ping; a summary of a mail is the answer. Discord takes 2,000 per message and the bot already splits | `MAX_SAID` in `events/store.py` |
| `discord_say` is a tool apart from `notify`, and is not offered from Discord itself, in an incognito conversation or a local-only one | `notify` is a ping that needs no answer; `discord_say` hands the conversation over, so it must be a conversation that can live on Discord (an incognito one is deleted, a local-only one must not leave). It is class `discord` (allow, refused when local-only, like threads) | `tools/discord_tools.py` |
| A run that delivers to Discord is told its answer is a message you will answer, and may end with a proposal | The other instructions say « nobody can answer a question now » and ask for a three-sentence summary, which suits a ping and nothing else | `INSTRUCTIONS_TALKING` (`triggers/message.py`, `timekeeping/schedules.py`) |
| Your reply in the conversation of a hook's run is an ordinary turn: all her tools, tainted only while a mail the run read is still in the prompt | The allow-list holds for the run and for the follow-up after one of its approvals (`Agent.restrictions`); a reply from you is not an event from outside. This is what lets « remind me an hour before » work without listing `remind` on the hook. Applying the list to your replies too is a one-line change in `Agent`, at the price of listing `remind` and `add_task` on each hook that talks | `Agent.restrictions`, `tests/test_deliver.py` |
| The server decides the Discord channel of an event, not the bot | One table (`events/routing.py`) serves the web page, the test message and the stream; the stream adds `channel` for the Discord client, read at delivery so a change applies to the next message even on an open stream. The bot keeps its own table only as the fallback for a server that does not say, and refuses any channel but the three choices | `api/events.py`, `clara_discord/bot.py` |
| `#approval` is not a choice, alerts cannot be switched off | What is in `#approval` is always waiting for your answer, so nothing else may bury it; an alert is the safety net, and turning it off would hide the thing that tells you the rest is broken. Alerts may move to another channel | `check_routes` |
| The page never holds a channel id | Ids stay in the bot's settings (the bot checks that its four channels exist and share a server); the page chooses only among the four names the bot already has, so a routing change creates no reach | `discord_routes` |
| The bot's heartbeat carries its channels' names and missing rights, in memory only | A wrong channel or a missing right is otherwise seen only in a log or after the `discord` alert; it costs one small JSON object a minute and nothing is stored | `ops/discord_report.py` |
| A test message goes where it names, from a source only the server sets, and the bot drops one older than two minutes | A test must show whether Discord accepts a post in that channel whatever the routes say; a client posting a notification cannot pass for one, and a bot that was away does not post it hours later | `TEST_SOURCE`, `deliver_test` |
| Outlook is removed: Gmail is the one mailbox | The owner asked for the Outlook connector to be deleted. Its module, its sign-in routes, its settings, its secrets, its alert and its tests went with it. The mail layer (`MailClient`, the mail tools, the gate classes, the hooks) is unchanged in shape, so another mailbox can be added as one connector module. Migration 0008 is not rewritten: a database that has it still allows the `outlook` kind, which nothing writes | `PROVIDERS` in `connectors/mail.py`; the rows above that name Outlook are the choices this one reverses |
